The most expensive part of our pricing engine was a product decision

Impact Analytics · 2024

How a B2B pricing engine went from 10 always-on, high-RAM workers to 3, and what I’d change if I did it again.

10 → 3permanent high-RAM workers

How a forecast used to run

I inherited a B2B pricing and inventory optimization tool while moving from business analysis into backend engineering. It did its job. It was also expensive to run.

For one discount forecast, the request went from the UI to the backend, to our BA layer, back to the backend and back to the UI. Four handoffs across two teams, and most of our failures happened right at those handoffs.

How one forecast used to run

  1. UIA user asks for a discount forecast
  2. BackendHandoffGenerates a CSV
  3. BA layerHandoffRuns the processing
  4. BackendHandoffGets the results back
  5. UIHandoffFinally shows the forecast

Four handoffs, two teams, one forecast. Most failures happened at the handoffs.

Predicting which tasks need a big worker

We couldn’t tell ahead of time which tasks would be heavy, so we treated every task as the worst case and kept 10 high-RAM workers running all the time.

Going through past runs, processing time mostly depended on things we already knew when a request came in: the CSV row count, the date range and the request volume. So I set a threshold. If a task was expected to cross 90% of a normal worker’s capacity, it went to a big worker.

Around 70% of tasks never needed a big worker, and there were zero failures after the change.

The routing rule

  1. Known at request timeCSV row count, date range, request volume
  2. Predicted memoryWill this task cross 90% of a normal worker?
Big workerOver 90%
Normal workerUnder 90%

About 70% of tasks never needed a big worker

And zero failures after the change

Removing the handoffs

I’d worked on both sides by then, so I could change the flow end to end. We dropped the CSV step, the BA layer wrote JSON the UI could read directly, and the API moved to FastAPI with every call async. Users could start a forecast and carry on while Pub/Sub workers ran it in the background.

BeforeAfter

Before

  1. UIRequest
  2. BackendBuilds a CSV
  3. BA layerProcesses it
  4. BackendPasses results back
  5. UIWaits on a spinner

After

  1. UIRequest, then keeps working
  2. BackendPasses data straight on
  3. BA layerWrites JSON the UI reads directly
  4. Pub/Sub workersRun it in the background, async

Drag to compare. The CSV step and the trip back through the backend are gone.

From 10 workers to 3

With the routing and the simpler flow in place, 10 permanent high-RAM workers became 3. Big workers only spun up when a task crossed the threshold.

The AWS bill went down. What I liked more was that the system now worked out how much compute a task needed, so we stopped guessing and paying for the worst case.

What I’d do differently

Everything above treats this as an engineering problem. If I did it again, I’d start from the product side and ask which product decisions made the system expensive.

Each plan had its own isolated workers because the product assumed one user drives an experiment on discounts. That isn’t how retail decides on discounts. The business judges plans against top-level metrics like revenue, margin and sell-through.

So I’d attach the outcome to the business: one forecast per department and time frame, computed as one big batch and read by everyone. I wrote the full story up on Medium.

The product decision behind the cost

How the tool worked

What I'd build now

One forecast per department and time frame, stored once, read by everyone.
